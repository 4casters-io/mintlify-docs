## What you are doing

This is the main **place** call: you send one or more **orders** to `/session/v2/place`. The sample body shows the usual case—**resting a new offer** on the board.

<Note>
  For mode-specific behavior, see [Place coins orders](/pages/coins-only/place-coins-orders) and [Switch player mode](/pages/coins-only/switch-player-mode).
</Note>

## Order types

`orderType` controls whether your order takes existing liquidity, rests on the book, or both:

| `orderType` | Behavior |
| --- | --- |
| `post` | **Maker-only.** Rests on the book — but **only if it would not cross** the current market. If it *would* match existing liquidity, it is **rejected and nothing rests** (see [If your `post` would cross](#if-your-post-would-cross-the-book) below). `post` never takes. |
| `limit` | **Take-then-rest.** Matches whatever liquidity it crosses right now, then rests any unfilled remainder on the book. This is the type to use if you want to join or take the current market and still leave a working offer. |
| `fillOrKill` | Match in full immediately or reject the whole order. Never rests. |
| `fillAndKill` | Match whatever crosses immediately, discard the remainder. Never rests. |

<Warning>
  `post` is **not** "the resting type" and `limit` is **not** "the taking type." Both can rest; the difference is that `post` refuses to take (it is dropped if it would cross), while `limit` takes what it can and rests the rest. If you want your offer to rest regardless of whether it crosses, use `limit`.
</Warning>

## If your `post` would cross the book

A `post` order only rests when its price does **not** cross the best available price on the other side. If it would cross, the API does **not** match it and does **not** rest it — instead you get **`HTTP 200` with an empty `matched` array and an empty `unmatched` object** (no `unmatched.orderID`). This is the expected maker-only outcome, not an error, so there is no `4xx` to catch.

There is **no probability/odds cap** here. American odds are valid for any magnitude between `100` and `100000` on either side (e.g. `-110`, `+250`, `-900` are all fine). Whether a `post` rests depends entirely on whether its price crosses the book — not on whether the odds are above or below even money.

**To rest on the favorite (negative-odds) side:** submit your real side and odds (e.g. `side: "yes"`, `odds: -900` for a ~90¢ bid) and price it so it does **not** cross the best opposing offer, or use `limit` if you are willing to take the crossing liquidity. The side you submit is always your real exposure — submitting the opposite outcome at the inverse price is the *opposite* bet, not an equivalent one.

**To detect a dropped `post`:** treat an empty `matched` **and** empty `unmatched` (no `orderID`) as "post-only rejected, would have crossed."

## Request body (field by field)

| Field | Meaning |
| --- | --- |
| `orders` | Array; most integrations send **one** order object while testing. |
| `orderType` | One of `post`, `limit`, `fillOrKill`, `fillAndKill` (see [Order types](#order-types)). |
| `gameID` | The game/market id—must exist in the system. |
| `type` | `moneyline`, `spread`, `total`, etc. |
| `odds` | American odds from **your** perspective (e.g. `-110`). Valid magnitude `100`–`100000`, either sign. |
| `risk` | Amount you risk on this offer. |
| `side` | Which side you back — this defines your real exposure. Valid values depend on the game; `team_a` is only a placeholder. |

## Example response

- `createdSessions` — one entry per submitted order.
- `matched` — instant fills (empty for a pure `post`).
- `unmatched` — what is still live: use `orderID` with **Cancel order** / **Look up single order**; `offered` / `remaining` show how much risk is still working.

<Note>
  The example below shows a `post` that **rested** — i.e. its `-110` price did **not** cross the book in that market. The same request in a market where `-110` crosses the best opposing offer would instead return empty `matched` and `unmatched` with no `orderID`. Always check for `unmatched.orderID` to confirm your offer is actually working.
</Note>

Replace sample ids and `side` with values from your environment before expecting a real fill.

## Request

<Card>
  **POST** `https://api.4cx.io/session/v2/place` <Badge color="green">POST</Badge>
</Card>

**Headers:** `Authorization`, `Content-Type: application/json`

<CodeGroup>
```json Request
{
  "orders": [
    {
      "orderType": "post",
      "gameID": "evt_001",
      "type": "moneyline",
      "odds": -110,
      "risk": 50,
      "side": "team_a"
    }
  ]
}
```

```json Response
{
  "data": {
    "createdSessions": [
      {
        "matched": [],
        "unmatched": {
          "filled": 0,
          "offered": 50,
          "remaining": 50,
          "orderID": "ord_001",
          "odds": -110
        }
      }
    ]
  }
}
```
</CodeGroup>
